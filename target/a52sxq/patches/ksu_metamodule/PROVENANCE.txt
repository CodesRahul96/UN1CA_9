What it does on this phone (5.4 kernel, erofs system/vendor/product/odm):
  - install (customize.sh, run by ksud): picks the aarch64 binary, creates a sparse 2 GB ext4 image modules.img
    (mke2fs -O ^has_journal) in /data/adb/modules/meta-overlayfs.
  - metainstall.sh (sourced by ksud for every later module install): copies the module's system/ vendor/ ...
    into the image (labels copied), the module itself stays in /data/adb/modules/<id>.
  - metamount.sh (ksud post-fs-data, after all post-fs-data scripts, before init's /system/etc/init post-fs-data
    actions such as k4-gpu-driver): loop-mounts the image and overlays /system, /vendor, /product, /odm with the
    enabled modules' content as lower layers (source "KSU", so KernelSU's umount feature recognises the mounts);
    child mounts are re-bound. Needs CONFIG_OVERLAY_FS, CONFIG_BLK_DEV_LOOP, CONFIG_EXT4_FS: all =y in the
    bone-machine 5.4.302 kernel (/proc/config.gz). erofs lower layers are fine (overlayfs only needs an upper/work
    dir on a writable fs, which it does not use here unless /data/adb/modules/.rw exists).
  - post-mount.sh: ksud kernel nuke-ext4-sysfs (supported by this ksud).
  Known limit: a module installed before the metamodule is not in the image and stays unmounted until reinstalled.

Alternatives looked at (all metamodules in the official KernelSU-Modules-Repo org):
  - meta-mm (Magic Mount, 7a72) v1.0.1-sprout: GitHub repo is a placeholder, its sourceUrl
    codeberg.org/ovo/meta-magic_mount is gone (404): no source for a GPL-3.0 binary, cannot be redistributed.
  - magic_mount_rs v4.0.2 (Apache-2.0): its mount binary dlopens libs/arm64-v8a/libchecker.so, a 2.4 MB Go blob
    without source in the repo, to verify a signature of the module and panics if that fails - an opaque binary in
    the boot path.
  - hybrid_mount v6.2.0 (Apache-2.0): three mount engines (OverlayFS, magic mount, Kasumi), 3.4 MB, web UI: far
    more than "mount the modules", more to go wrong in a default.
